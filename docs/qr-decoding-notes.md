# 二维码解码踩坑记

> 从「本地测试 10/10 却真机一个都扫不出」到「两台设备横竖屏全通」的完整记录。
>
> 如果你也在写自己的二维码解码器，或者遇到"扫不出来"的问题，这份记录能帮你少走几小时弯路。

---

## 为什么自己写

不引 Google ML Kit，不引 ZXing，理由只有一个：**体积**。

- 引 ML Kit：APK 至少涨 3~10 MB，还要联网拉模型
- 引 ZXing：约 500 KB，且要处理 Android 依赖
- 自己写：**纯 Java 约 39 KB 源码，APK 总共 72.6 KB**

代价是要自己啃完格式信息、掩码、数据块、透视变换——也就是下面这些坑。

---

## 先说最重要的一条教训

**合成图能解 ≠ 真实照片能解。这是两种完全不同的测试。**

我用程序生成的干净二维码测了 10/10 全过，就以为成了。到了真机上，一个都扫不出，连续返工四五个版本。

两者差在：

| | 合成图 | 真机拍屏 |
|---|---|---|
| 位错误 | 零 | 必然有几位 |
| 几何 | 完美正交 | 透视畸形 |
| 颜色 | 标准白底黑块 | 可能是反色 |
| 背景 | 干净 | 有文字、边框、反光 |

**正确的验证顺序**：先生成图自测 → 再用**真机拍屏截图**跑回归 → 最后才上真机实时扫。

只做第一步就交付，等于没测。

## 坑 1：直角顶点取反（一行代码，全盘皆输）

**现象**：本地合成图 0/7 全失败，连第一个定位图形都找不到。

**根因**：三个寻像图形构成等腰直角三角形。要确定哪个是"左上角"，得先找**直角顶点**。

我写成了「斜边对应的两个端点之一的对面」——取反了。

正确逻辑：

```
三条边长排序 → 最长边是斜边 → 斜边对面的那个顶点才是直角顶点
```

**修法**：斜边对面取顶点。修完 7/7 通过。

**教训**：几何代码写完要用已知答案的样例先验一遍，别等真机。

---

## 坑 2：按 moduleSize 精确分桶，把真三点组拆散了

**现象**：整图里明明有三个标准定位图形，程序就是找不到一组。

**根因**：我用 `round(moduleSize × 10)` 作为分桶 key，只在同一个桶里找三点组。

真实照片里三个角的 moduleSize 有透视差异，实测一帧 1440×1920 的画面：

```
左上   moduleSize = 12.43  → 桶 124
右上   moduleSize = 11.86  → 桶 119
左下   moduleSize = 12.66  → 桶 127
```

**三个角落进了三个不同的桶，永远凑不成一组。**

**修法**：取消精确分桶，改成「宽松筛选 + 严格验证」两段式：

1. 先按 hits（被扫描线命中的次数）和 moduleSize 排序，只留前 18 个候选点
2. 枚举所有三点组，用**宽松**的几何容差筛（允许 20% 边长偏差、60% 模块尺寸偏差）
3. 对每组采样后**强校验三个角的寻像图形是否真的存在**——这一步能过滤掉绝大部分假候选

关键是第 3 步：既然错判会被验证环节挡掉，前面就不必卡得太死。

## 坑 3：反色码（深色主题下的陷阱）

**现象**：屏幕上肉眼看得清清楚楚的二维码，任何解码器都读不出。

**根因**：**深色终端主题下，二维码变成了「深底浅块」**。

生成的是标准黑块白底。但终端里用字符渲染后，在深色主题下变成了浅色块 + 深色背景。

验证很直接——同一张图反色前后，用独立解码器（pyzbar）对照：

| 样本 | pyzbar 结果 |
|---|---|
| 标准码（白底黑块） | ✅ 解出 |
| **反色码（黑底白块）** | ❌ NULL |
| 模糊 2.5px 的标准码 | ✅ 仍能解 |

**模糊不影响，反色直接全废。**

**修法**：解码入口先按原图解一次，失败就把 255-x 反色再解一次。

```java
public static Result decode(byte[] gray, int w, int h) {
    Result r = decodeOnce(gray, w, h);
    if (r != null) return r;
    byte[] inverted = new byte[gray.length];
    for (int i = 0; i < gray.length; i++) {
        inverted[i] = (byte)(255 - (gray[i] & 0xFF));
    }
    return decodeOnce(inverted, w, h);
}
```

顺带一个结论：**不要在深色终端里用字符画显示二维码给人扫**。用图片查看器打开 PNG 更靠谱。

## 坑 4：整图检测被周围文字干扰

**现象**：把二维码从整张照片里裁出来能解，但直接喂整张图解不出——自己的解码器和 pyzbar 都一样。

**根因**：终端窗口有大量文字和边框，会产生一堆「1:1:3:1:1」的假定位图形。整图检测时真码被淹没。

实测同一张 1440×1920 照片：

| 裁切方式 | 结果 |
|---|---|
| 精确裁出二维码区域 | ✅ 解出 |
| 中心 45% / 55% / 65% / 75% 正方形 | ❌ 全失败 |
| 以码中心为准的固定边长正方形 | ❌ 全失败 |

**修法**：靠坑 2 的「严格验证」来解决，而不是靠裁切。裁切只是辅助——现在保留「全图 → 中心 70%」两级重试。

## 坑 5：透视畸变（最深的坑，也是最终的答案）

**现象**：日志显示候选三点组全部通过寻像图形校验，但 `decodeMatrix` 就是失败。

```
[QRDBG] decode: dim=37 finder patterns OK
[QRDBG] skip: decodeMatrix failed dim=37
```

**根因**：**手机斜着拍显示器，画面有透视畸变。**

采样用的是**仿射变换**（3 个点决定）。仿射只能表达平移/旋转/缩放/错切，表达不了透视的「近大远小」。

结果就是：三个角定位准确、格线对上，但**越往中间和右下，模块偏移越大**，最后整片读错。一个模块错半格，数据就废了。

而没有实现 Reed-Solomon 纠错（见坑 6），所以是零容忍。

**修法**：找到**对齐图形（alignment pattern）**作为第 4 个锚点，做**单应变换**（homography）。

```
三个定位图形中心 → (3.5, 3.5), (dim-3.5, 3.5), (3.5, dim-3.5)
对齐图形中心     → (ac+0.5, ac+0.5)     ← 第 4 点，这是关键
```

四点求 8 参数单应矩阵：

```
x' = (a·x + b·y + c) / (g·x + h·y + 1)
y' = (d·x + e·y + f) / (g·x + h·y + 1)
```

对齐图形（version ≥ 2 才有）的定位方式：先用仿射估个大概位置，再在 ±3 模块范围内搜索 5×5 的黑框-白环-黑心图案。

**加上这一步，真机拍屏立刻就能解出来了。**

```
[QRDBG] perspective: align pred=(665,958) found=(646,990)
[QRDBG] decoded(perspective) dim=37
```

**教训**：手写解码器如果只做仿射，就注定只能解"正对着拍"的码。

## 坑 6：没有实现 Reed-Solomon 纠错

**这是目前仍然欠缺的部分**，也是为什么坑 5 会致命。

标准解码器会算 syndrome，用 Berlekamp-Massey 求错误定位多项式，Chien 搜索找错误位置，Forney 算错误值，然后纠错。Version 5 的 M 级纠错能纠正约 10 个码字错误。

本实现没做这一步，所以**任何一位读错都直接失败**。这也是为什么干净的合成图毫无问题、真实照片一步不差就全崩。

如果要提升鲁棒性（很远、很糊、有光斑），补 RS 纠错比继续调采样参数更有效。

## 坑 7：静默 catch 把 bug 藏起来了

**现象**：解码线程"看起来在跑"，但永远没结果，日志里什么都没有。

**根因**：线程里写了

```java
} catch (Throwable ignored) { }
```

而实际上缓冲区根本没分配，每帧都抛 NPE，被吞得干干净净。

**修法**：

```java
} catch (Throwable e) {
    dbg("decode error: " + e);   // 必须留痕
}
```

**教训**：常驻线程的兜底 catch 一定要打日志。否则表现就是"稳定运行、毫无产出"，极难排查。

## 坑 8：TextureView.setTransform() 在部分设备上无效

**现象**：相机预览始终横向。日志显示旋转角度算得完全正确：

```
view=1080x2214  preview=1280x960  sensor=90  dispRot=0  rotate=90
```

参数全对，画面就是不转。

**根因**：`TextureView.setTransform(Matrix)` 在该测试设备上不生效。

**修法**：**放弃 TextureView 渲染，改用逐像素旋转。**

```
Camera2 YUV_420_888 → 手动旋转成灰度数组 → 转 ARGB → 画到自绘 View
```

旋转在像素层面完成，不依赖任何系统矩阵，结果完全可预期。代价是 CPU 开销，换来的是确定性。

**教训**：如果一个系统 API 的参数全对但效果为零，先怀疑这个 API 在当前设备上能不能用，而不是继续调参数。

## 坑 9：预览帧率从 16 拉到 30

**现象**：扫码页预览明显卡顿。

**根因**（三处叠加）：

1. **每帧新建 11 MB 位图**：1920×1440 全分辨率转 ARGB，每次解码都新建 Bitmap，GC 抖动
2. **`setImageBitmap` 每帧都调**：它会触发 `requestLayout`，这是主要卡顿源
3. **解码和预览共用一条线程**：一次解码 100 ms，画面直接冻住

**修法**：

| 改动 | 效果 |
|---|---|
| 预览按 1/3 降采样，复用 Bitmap 对象 | 位图从 11 MB 降到 0.7 MB |
| 预览改用自绘 View + `invalidate()` | 不再触发布局测量 |
| 解码移到独立 HandlerThread，限速 6 次/秒 | 预览不再被解码阻塞 |
| 采样微调从 9 组减到 1 组（透视已覆盖） | 单次解码开销下降 |

**结果**：16 fps → **29~30 fps**（相机满帧）。

## 验证数据留档

解码器回归（桌面 JVM，1440×1920 真机拍屏帧）：

| 测试样本 | 结果 |
|---|---|
| 真机拍屏，正对 | ✅ 解出 |
| 真机拍屏，斜拍 | ✅ 解出（透视校正生效） |
| 686×686 生成图 | ✅ 解出 |
| 生成图及其反色版 | ✅ 均解出 |
| 早期 480×640 低清帧 | ❌ 预期失败 |

最后一张失败是合理的：640 宽画面里二维码只占约 250 px，37 个模块 → **6.7 px/模块**，太密了。改到 1920×1440 后约 **13 px/模块**，才稳定。

**经验值：每个模块至少 10 px 才靠得住。**
